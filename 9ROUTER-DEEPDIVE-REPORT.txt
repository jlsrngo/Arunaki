PART 1 — MEKANISME LOGIN / AUTENTIKASI  (FOKUS UTAMA)
================================================================================

9Router adalah PROXY lokal. Ada DUA arah autentikasi yang sering tertukar:

  (A) Client (Claude Code, Codex, Cursor, Cline...)  --> 9Router : pakai API key
  (B) 9Router                                        --> Provider (Anthropic,
      OpenAI, AWS Kiro, GitHub Copilot, Google, dll) : 9Router yang login

CLI TIDAK PERNAH LOGIN LANGSUNG KE PROVIDER. CLI cukup kasih endpoint + API key
ke 9Router; semua kredensial provider hidup di dalam 9Router.

--------------------------------------------------------------------------------
1A. ARAH CLI/IDE -> 9Router
--------------------------------------------------------------------------------

1) Endpoint yang disetel ke CLI:  http://localhost:20128/v1
   Port default: 20128 (docs/README) / 20127 (script dev root — beda, lihat PART 5).

2) API KEY berformat machine-bound.
   File: src/shared/utils/apiKey.js
     Format : sk-{machineId16}-{keyId6}-{crc8}
     crc8   : HMAC-SHA256(API_KEY_SECRET, machineId + keyId) di-slice 8 char
              -> key "terikat mesin" dan tidak bisa dipalsukan tanpa secret.
     parseApiKey() juga menerima format lama "sk-{random8}".
   Validasi: src/sse/services/auth.js:364 isValidApiKey() -> apiKeysRepo.validateApiKey
   Ekstraksi (src/sse/services/auth.js:345):
     - header "Authorization: Bearer sk-..."   (OpenAI-style)
     - header "x-api-key sk-..."               (Anthropic-style)
   Catatan: kalau REQUIRE_API_KEY tidak aktif, validasi bisa dilewati (local dev).

3) Dua token "mesin" lain yang dipakai untuk komunikasi internal:
   - x-9r-cli-token  : machineId di-salt "9r-cli-auth"
                       -> membolehkan proses CLI lokal mengakses API dashboard
                          yang biasanya butuh session (src/dashboardGuard.js:7).
   - PEER_TOKEN      : 24 random byte per-process (custom-server.js:13),
                       dipublikasikan sebagai NINEROUTER_PEER_TOKEN; dipakai
                       MITM <-> server sebagai header x-9r-peer-token
                       (di-strip custom-server.js:66-69 sebelum masuk Next).

4) "Pemasangan" CLI ditulis OTOMATIS oleh dashboard (halaman CLI Tools).
   Pola semua route: GET = deteksi & lapor, POST = merge HANYA field 9router,
   DELETE = hapus HANYA field 9router (tidak pernah merusak config user).

   a. Claude Code  -> src/app/api/cli-tools/claude-settings/route.js
      Tulis ~/.claude/settings.json :
         env.ANTHROPIC_BASE_URL = "http://localhost:20128/v1"  (selalu diakhiri /v1)
         env.ANTHROPIC_AUTH_TOKEN = "sk-..."  (token lama user TIDAK ditimpa)
         hasCompletedOnboarding = true
         CLAUDE_CODE_AUTO_COMPACT_WINDOW (opsional)
      Tulis ~/.claude.json : merge mcpServers (plugin "exa") -- disimpan di sini
      karena Claude Code membaca mcpServers dari ~/.claude.json, bukan settings.json.
      Reset menghapus 7 key env (RESET_ENV_KEYS).

   b. OpenAI Codex -> src/app/api/cli-tools/codex-settings/route.js
      Tulis ~/.codex/config.toml (pakai pustaka confbox, edit terstruktur):
         model_provider = "9router"
         [model_providers.9router]
           base_url   = "http://localhost:20128/v1"
           wire_api   = "responses"
           http_headers.Authorization = "Bearer sk-..."
         agents.default_subagent_model = ...
      Alasan header statik: provider custom di Codex mengabaikan auth.json,
      jadi API key harus dikirim sebagai header tetap.
      DELETE hanya berlaku jika model_provider masih "9router".

   c. Route sejenis: opencode, cline, copilot, kilo, droid, crush, grok-build,
      openclaw, hermes, devin, deepseek-tui, jcode, forge, omp, pi, smelt,
      cowork, codewhale, deepseek... (lihat src/app/api/cli-tools/*).

5) CLI launcher `9router connect <url>` (cli/src/cli/commands/connect.js):
   - login ke 9Router remote memakai password dashboard,
   - membuat/memakai ulang API key bernama "cli-<hostname>",
   - menulis config semua tool CLI (backup dulu jd *.bak-9router).

--- B1. OAuth authorization_code + PKCE (login normal) -----------------------

Registrasi 25 provider (src/lib/oauth/providers/index.js:34-60):
  claude, codex, xai, grok-cli, muse, gemini-cli, antigravity, iflow, qoder,
  qoder-cn, github, kiro, cursor, kimi, kilocode, cline, clinepass, gitlab,
  codebuddy-cn, codebuddy-intl, kimchi, trae, windsurf, zed, glm

API dinamis: src/app/api/oauth/[provider]/[action]/route.js
  GET  : authorize | start-proxy | poll-status | stop-proxy | ide-status
         | device-code
  POST : register-session | exchange | poll | manual-code

Alur (provider/index.js:91-147):
  generateAuthData(name, redirectUri, meta)
    -> generatePKCE()  (S256, src/lib/oauth/utils/pkce.js:8-39)
    -> buildAuthUrl(config, redirectUri, state, codeChallenge)
    -> user membuka authUrl di browser, authorize, kembali ke /callback
       (src/app/callback/page.js)
  exchangeTokens(name, code, redirectUri, codeVerifier, state, meta)
    -> provider.exchangeToken(...)   -> token JSON
    -> provider.postExchange(tokens) -> data tambahan (akun info, mint key, dll)
    -> provider.mapTokens(tokens, extra) -> { accessToken, refreshToken,
       expiresIn, ... providerSpecificData }
    -> disimpan sebagai baris baru di tabel providerConnections.

  flowType per provider: "authorization_code_pkce" | "device_code" | lainnya.
  Pengecualian khusus (providers/index.js:96-125):
    - Trae pakai loginTraceID sbg state callback, bukan PKCE state.
    - Zed : codeVerifier membawa private key RSA encoded (bukan PKCE verifier),
            config.systemId ikut di-thread sampai ke penyimpanan connection.
    - "start-proxy"/"poll-status": untuk provider yang mewajibkan redirect ke
      loopback port tetap (fixedPort), 9Router menjalankan auth proxy lokal
      (src/lib/oauth/utils/server.js, 37.9KB) untuk menangkap callback.

  Contoh konkret Claude (src/lib/oauth/providers/claude.js):
    buildAuthUrl -> https://claude.ai/oauth/code/authorize ?
      code=true & client_id=<milik Claude Code> & response_type=code
      & redirect_uri & scope & code_challenge & code_challenge_method=S256 & state
    exchangeToken -> POST tokenUrl JSON { code, state, grant_type:
      "authorization_code", client_id, redirect_uri, code_verifier }
    -> mapTokens -> { accessToken, refreshToken, expiresIn, scope }
  Artinya: 9Router memakai client_id milik CLI resmi, sehingga login user
  menghasilkan token berlangganan (Pro/Max) yang sah.

--- B6. MITM Bridge (memakai langganan IDE TANPA OAuth) ------------------------
  src/mitm/ (manager.js 32KB, server.js 15.9KB, handlers/*)
  Ide: intercept trafik HTTPS lokal dari IDE (Antigravity, GitHub Copilot,
  Kiro IDE, Cursor) lalu alihkan ke 9Router.

  Mekanisme:
   1. Generate local Root CA (node-forge/selfsigned) -> src/mitm/cert/
      (generate.js, rootCA.js, install.js) -> dipasang ke trust store sistem.
   2. Override DNS utk target host (src/mitm/dns/dnsConfig.js):
        daily-cloudcode-pa.googleapis.com / cloudcode-pa.googleapis.com  (Antigravity)
        api.individual.githubcopilot.com                                 (Copilot)
        runtime.us-east-1.kiro.dev / q.us-east-1... / codewhisperer...   (Kiro)
        api2.cursor.sh                                                   (Cursor)
   3. HTTPS server lokal port 443 (Windows fallback 8443) dengan SNI callback
      -> decrypt -> hanya "chat request" yang di-rewrite
      (isChatRequest() punya case khusus Kiro via header x-amz-target),
      selain itu dipassthrough utuh.
   4. Request diubah & dikirim ke 9Router (src/mitm/handlers/base.js:19-37):
        STRIP_HEADERS membuang "authorization" milik IDE
        -> mengganti dengan Authorization: Bearer ${ROUTER_API_KEY}
        -> POST http://localhost:20128/v1/chat/completions
   5. Respons di-pipe balik sebagai SSE (base.js:43+ pipeSSE) sehingga IDE
      merasa sedang bicara dgn vendor asli.
   6. Proteksi loopback: header "x-request-source: local" (server.js:21),
      health check GET /_mitm_health, PID+LOCK file, restart max 5x dgn
      backoff [5s,10s,20s,30s,60s], password di-encrypt AES-256-GCM.

  HASIL AKHIR: kredensial yang dipakai utk memberi jawaban adalah milik
  9Router (route B1-B5), bukan token IDE yang di-strip. IDE hanya menjadi
  "pintu masuk". (Catatan kebijakan ToS masing-masing tool tetap berlaku.)

--- B7. Refresh token: bagaimana login tetap hidup -----------------------------

  Tiga lapis:

  (1) PROAKTIF per-request — src/sse/services/tokenRefresh.js:224
      checkAndRefreshToken(provider, credentials) dipanggil di account loop
      (src/sse/handlers/chat.js:255) SEBELUM request dikirim.
      - Buffer kadaluarsa 5 menit (open-sse/services/tokenRefresh.js:43),
        lead per-provider via getRefreshLeadMs().
      - Penting: sebelum refresh, credential "mengadopsi" refresh token
        terbaru dari DB (open-sse RT disimpan; OpenAI mencabut seluruh sesi
        kalau refresh token dipakai dua kali) — tokenRefresh.js:230-247.
      - Single-flight lock per "provider:connectionId" (oauthCredentialManager
        .js:134-147) -> refresh paralel tidak duplikat.
      - mergeRefreshedCredentials() menghitung ulang expiresAt +
        lastRefreshAt.

  (2) BACKGROUND scheduler — src/sse/services/backgroundTokenRefresh.js
      Interval tiap 5 menit, delay awal 10s, lead 30 menit
      (BACKGROUND_REFRESH_LEAD_MS). Kandidat: authType "oauth" + punya
      refreshToken + expiry dalam max(providerLead, 30menit).
      - Dijalankan SEKUENSIAL + jitter utk tidak membanjiri Google
        (antigravity/gemini-cli: 12s + 0-4s; lainnya 1.5s + 0.2s).
      - Fail-open per koneksi; dimatikan via DISABLE_BACKGROUND_TOKEN_REFRESH
        atau saat build/edge runtime.

  (3) REAKTIF di pipeline — open-sse/handlers/chatCore.js:424-469
      HTTP 401/403 dari upstream -> refreshWithRetry(executor.refreshCredentials, 3)
      -> mutasi credential di tengah retry (utk provider rotasi RT)
      -> 1x percobaan execute ulang. Baru kalau masih gagal -> fallback akun.

  Registry refresh: open-sse/services/tokenRefresh.js:135-160 REFRESH_HANDLERS
  untuk gemini-cli, antigravity, claude, codex, iflow, github, kiro, xai,
  grok-cli, gcli, codebuddy-cn/intl, trae, cline, clinepass, zed, windsurf,
  kimi, vertex/vertex-partner (mint JWT service-account sendiri).
  Executor-side grant: open-sse/executors/default.js:52-67 (JSON vs form encoding,
  refreshIflow/Kiro/Cline/Kimi/Kilocode).
  Codex punya maxRefreshAgeMs = 8 hari (refresh paksa walau belum expired).

  Quota yang memicu fallback login-berikutnya:
  - open-sse/services/usage/* (claude, codex, google, github, kiro, kimi, grok,
    glm, deepseek, groq, minimax, zed, ...). Claude: endpoint OAuth utama +
    User-Agent "claude-cli/<ver> (external, cli)" + cache 5 menit/token +
    cooldown 180s sesudah 429 di endpoint quota.
  - antigravityQuota.js: circuit breaker "3 strike 409/429 dalam 60 detik ->
    blokir 15 menit" + cache {remainingPercentage, resetAt} yang dibaca oleh
    pre-filter auth (auth.js:92-99) supaya akun habis dilewati tanpa request.

3.1 MODEL NAMING
  Format: <prefix>/<model>  contoh: kr/claude-sonnet-4.5, cc/claude-opus-4-7,
  glm/glm-4.7, oc/<auto>, cu/composer-2.5.
  open-sse/services/model.js — parseModel() -> {provider, model}.
  Kalau TIDAK ada "/" -> cek COMBO dulu (src/sse/services/model.js:71-76
  mengembalikan provider:null sebagai sinyal "ini combo") -> baru alias ->
  baru inferensi prefix regex (MODEL_PREFIX_PROVIDERS: gpt-* -> codex/openai,
  claude-* -> anthropic, gemini-* -> gemini, deepseek-* -> openrouter).
  User-defined provider node boleh bikin prefix sendiri kecuali
  RESERVED_PROVIDER_PREFIXES (node bernama "openai" tidak bisa membajak builtin).

3.2 FALLBACK (4 tingkat)
  L0 model string -> combo / single / capacity-adapter
  L1 MODEl dalam combo (open-sse/services/combo.js:280-382):
     - rotasi round-robin dgn stickyLimit (state in-memory comboRotationState)
     - reorderByCapabilities menstabil-kan urutan: model dgn capability lengkap
       ke tier 0, hard-cap saja tier 1, sisanya tier 2 (model tidak pernah dibuang)
     - cek error dgn checkFallbackError -> {shouldFallback, cooldownMs}
     - 502/503/504 transient cooldown <=5s -> tidur dulu lalu coba berikutnya
     - semua gagal -> 503 / status terakhir + retryAfter terkecil
     Fusion strategy: fan-out paralel non-streaming -> panel quorum + grace
     -> kalau >=2 jawaban -> panggil JUDGE LLM utk menyintesis (combo.js:547-625)
  L1b capacity adapter: kalau tak ada model dgn modality yang diminta -> tambah
     model pool + strip history sesuai context window adapter
  L2 AKUN dalam satu provider (sse/services/auth.js getProviderCredentials):
     strategi preferredConnectionId -> round-robin -> fill-first (priority).
     Filter: exclude, model lock (modelLock_<model>/modelLock___all), codex
     enabledModels, antigravity quota cache. Selector dijaga MUTEX.
  L3 KLASIFIKASI ERROR (open-sse/services/accountFallback.js + config/errorConfig.js):
     rules teks dulu baru status; 4xx selain 401/402/403/429 -> TIDAK fallback
     (error per-request, mendingin akun justru menyembunyikan penyebab);
     selain itu -> cooldown transient, bisa exponential backoff sampai batas.

  PENTING: "3-tier Subscription -> Cheap -> Free" yang dipromosikan di README
  adalah MEKANISME DOKUMEN/URUTAN COMBO MILIK USER, bukan kode. Grep
  costTier/priceTier/PROVIDER_TIER tidak ada. Tiering terealisasi lewat
  urutan combo + fallback akun + kategori registry ("free"|"freeTier"|"apikey"|"oauth").

3.3 TRANSLATOR (open-sse/translator/)

   deployment publik wajib ganti INITIAL_PASSWORD/JWT_SECRET.

   harus di-set di produksi.
10. Regex nama combo diduplikat 3× (api/combos/route.js:7, [id]/route.js:6,
    comboPresets.js:10) — rawan drift.
11. Keamanan MITM: memasang Root CA sistem dan membaca trafik IDE lokal.
    Ini area sensitif baik secara teknis maupun kebijakan pemakaian tiap vendor.

KESIMPULAN SINGKAT (bagian login)
--------------------------------------------------------------------------------
9Router "bisa login ke CLI/provider lain" lewat empat strategi bertingkat:
  (1) Meniru login OAuth resmi tiap vendor (PKCE/device-code) memakai
      client_id milik CLI resmi -> token langganan sah.
  (2) MENGAMBIL token yang SUDAH tersimpan di mesin user dari cache
      Kiro (~/.aws/sso/cache), Cursor (state.vscdb), Codex (auth.json),
      iFlow (cookie), dsb — inilah cara termurah & paling umum.
  (3) Menerima API key tempelan utk 40+ provider berbayar.
  (4) Menyamar sebagai endpoint lokal bagi CLI (endpoint + API key terikat
      mesin) sehingga CLI cukup "login" ke 9Router sekali, dan 9Router yang
      mengurus semua kredensial, refresh, quota, dan fallback di belakangnya.
